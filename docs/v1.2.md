## Qué queda listo

El botón abre una ventana JRPG con un cofre original hecho en CSS, apertura de 900 ms, luz dorada, destello, botón para omitir y respeto a movimiento reducido. La consulta se realiza al abrirlo. Incluye reintento, reconsulta y regreso a la taberna. Escape cierra la ventana y deja disponible el cofre.

Solo se cambia la rama de victoria final de `finishBattle`. Las reglas de combate, los dos primeros desenlaces, datos, habilidades, fondos, sprites, taberna y módulos de animación permanecen intactos. No se añaden bucles de renderizado. La animación CSS no bloquea los turnos ni modifica PV/PM.

## Modelo de seguridad

La invitación es una credencial de acceso: quien posea ese enlace puede consultar esa asignación. No reenviar enlaces ajenos ni publicar el archivo de distribución. El combate local no prueba identidad ni victoria; un usuario técnico puede anticipar su propia consulta. CORS limita el uso desde otros sitios, pero **no** es autenticación. La protección real es el token aleatorio de 256 bits y la búsqueda individual por su SHA-256.

El fragmento no viaja en la petición HTTP a GitHub Pages. El cliente solo envía el token en un POST HTTPS a la función configurada, sin cookies ni referrer, con caché desactivada. No hay analítica ni registro de tokens/resultados. No habilitar trazas de cuerpos HTTP en servicios o proxies. El enlace seguirá presente en la barra e historial del navegador: usar un dispositivo de confianza.

Las cuatro tablas viven en `draw_private`, con RLS activada y sin permisos directos para `anon`, `authenticated` ni `service_role`. No añadir ese esquema a los esquemas expuestos de Data API. La única RPC pública es `reveal_draw`, ejecutable solo por `service_role`, de tipo invoker; delega en una función definer privada de búsqueda individual con `search_path` vacío. No existe una RPC que liste asignaciones. El organizador opera por conexión PostgreSQL privada y debe proteger sus credenciales y copias.

`commit_draw` bloquea concurrentemente por ID, inserta todo en una transacción y bloquea el sorteo. Las restricciones PK/UNIQUE/FK, los recuentos y `giver <> recipient` garantizan cobertura uno a uno. Triggers impiden cambios accidentales posteriores de participantes, asignaciones o bloqueo. Reenviar exactamente el mismo payload es idempotente; otro payload para ese ID se rechaza. Un administrador de base de datos con poderes de propietario puede cambiar el esquema: no es una protección contra el propietario malicioso.

El algoritmo usa Fisher–Yates con `crypto.randomInt`, rechazando permutaciones con puntos fijos. Al condicionar una permutación uniforme a no tener puntos fijos, todos los desarreglos válidos siguen siendo equiprobables (no se restringe a un ciclo). Los tokens usan `crypto.randomBytes(32)` y se comprueba que sean distintos.

## 1. Preparar Supabase de pruebas

Primero utilizar un proyecto y un ID exclusivos de pruebas, nunca la lista real. Crear el proyecto desde el panel de Supabase y conservar su contraseña de base de datos en un gestor seguro. Instalar la CLI oficial de Supabase según su documentación actual; requiere acceso a la cuenta. Desde la raíz del repositorio:

```sh
supabase login
supabase link --project-ref REFERENCIA_DEL_PROYECTO_DE_PRUEBAS
supabase db push --dry-run
supabase db push
```

El primer push revisa las migraciones pendientes; el segundo aplica la migración. No ejecutar comandos de reset sobre producción. Alternativa: ejecutar el archivo SQL completo una vez en SQL Editor como administrador. No repetir su contenido manualmente si ya figura aplicado. La migración es transaccional; Supabase lleva su historial.

Mantener `draw_private` fuera de los esquemas expuestos en Data API. El esquema público debe seguir expuesto para la RPC, cuya ejecución pública está revocada.

## 2. Secretos y Edge Function

En el panel del proyecto, crear/obtener una clave secreta de servidor `sb_secret_…`. Copiar `supabase/functions/.env.example` a un archivo **fuera del repositorio** y rellenar allí:

- `DRAW_SERVICE_KEY`: clave secreta, solo en el servidor.
- `ALLOWED_ORIGIN`: `https://davidgallegogp-collab.github.io` (sin ruta ni barra final).

`SUPABASE_URL` lo proporciona el entorno de Edge Functions. Para un ensayo en otro dominio, usar exactamente ese origen. No enviar estas claves por chat, no ponerlas en JavaScript y no pegarlas en comandos que queden en el historial.

```sh
supabase secrets set --env-file /RUTA_PRIVADA/edge.env
supabase functions deploy reveal-draw
```

`config.toml` define `verify_jwt = false` únicamente para esta función: sus visitantes no tienen una sesión Supabase; la función valida la capacidad de acceso del enlace. Mantener esa configuración al desplegar. La clave secreta se usa en el header `apikey` de la llamada del servidor a Data API; no es un JWT de usuario. Las respuestas contienen solo `{ recipient: { name, spriteKey } }`, con `no-store`, o un error genérico.

## 3. Lista y preparación local

Se necesita Node.js 22 o posterior. Instalar la única dependencia administrativa, fuera del flujo del navegador:

```sh
npm ci --prefix tools/sorteo
```

Crear una carpeta privada **fuera del checkout**, por ejemplo `/RUTA_PRIVADA/evento`. Guardar allí la lista real a partir de `participantes.example.json`. Ese ejemplo contiene solo dos nombres inventados, marcados como ejemplo; no se ejecuta automáticamente.

Cada entrada tiene `id` estable, `name` visible y `spriteKey` opcional. No usar índices del RPG. Nombres e IDs duplicados se rechazan. Se admiten entre 2 y 1.000 personas. Claves de sprite válidas actualmente: `david`, `noelia`, `jordux`, `pablo`, `villa`, `jesus`, `carlos`, `lucia`, `manu`, `maria`, `oscar`, `lobato`, `guarriadna`, `ari`, `alba`. Usar `null` si no corresponde ninguno. No asignar un sprite solo porque el nombre se parezca.

```sh
node tools/sorteo/admin.mjs prepare /RUTA_PRIVADA/evento ID_DEL_SORTEO /RUTA_PRIVADA/participantes.real.json
```

Este comando genera **una sola vez** `journal.json`, con la asignación preparada, tokens originales, hashes e ID de operación. No accede a la red. Un segundo `prepare` en la misma carpeta falla y no sobrescribe el archivo. Conservar una copia cifrada antes de confirmar. No borrar la copia para «solucionar» un error de red.

El directorio se restringe a permisos 700 y los archivos a 600 en sistemas POSIX. En Windows, proteger también su ACL y el disco. Las carpetas privadas y archivos de recuperación nunca se suben al repositorio, aunque `.gitignore` los excluya.

## 4. Confirmar y obtener enlaces

Copiar `tools/sorteo/.env.example` fuera del repositorio. Configurar:

- `DATABASE_URL`: cadena PostgreSQL de Supabase para un administrador del proyecto, desde Connect. Usar conexión directa o session pooler según conectividad. No usar la clave API como contraseña.
- `GAME_URL`: `https://davidgallegogp-collab.github.io/amigo-invisible-rpg/`.

La herramienta verifica TLS (`verify-full`). Si la conexión necesita la CA del proyecto, descargarla desde el panel y usar `NODE_EXTRA_CA_CERTS=/RUTA_PRIVADA/ca.crt`; no desactivar la verificación TLS. Mantener el archivo de entorno con permisos privados. Node lo carga sin mostrarlo:

```sh
node --env-file=/RUTA_PRIVADA/admin.env tools/sorteo/admin.mjs commit /RUTA_PRIVADA/evento
node --env-file=/RUTA_PRIVADA/admin.env tools/sorteo/admin.mjs status /RUTA_PRIVADA/evento
node --env-file=/RUTA_PRIVADA/admin.env tools/sorteo/admin.mjs export /RUTA_PRIVADA/evento
```

`commit` confirma exactamente el journal guardado y bloquea el sorteo. Si se corta la conexión antes de saber el resultado, repetir **ese mismo comando con esa misma carpeta**. Nunca volver a generar participantes/asignaciones para resolverlo. `status` verifica bloqueo, digest del payload e invitaciones actuales. `export` hace esas comprobaciones antes de escribir `invitaciones.json`: solo nombre del participante y su enlace, **sin destinatario**. Distribuir cada entrada individualmente por WhatsApp, manualmente; no enviar el archivo entero al grupo.

Una operación local crea `.admin.lock` para excluir comandos simultáneos. Tras un cierre forzado, confirmar que no queda ningún proceso administrativo ejecutándose antes de quitar ese lock. Si quedó un `.tmp`, conservarlo como copia para revisión y retirar solo ese temporal; no borrar `journal.json` ni un `rotation-*.json`. Ante errores, no se imprimen detalles internos para evitar filtrar consultas o credenciales. Revisar primero configuración/permisos y usar el mismo journal.

## 6. Copias de seguridad y sustitución de invitaciones

Conservar cifrados y separados del repositorio: journal, operaciones de rotación, lista validada, archivo de distribución vigente y configuración privada. Restringir quién los lee: el journal contiene todas las asignaciones y tokens. Las copias de Supabase deben incluir el esquema `draw_private` (comprobarlo expresamente); la base guarda hashes, por lo que una copia de DB por sí sola no recupera los enlaces originales.

Si una persona pierde o expone su enlace, sustituirlo con un nombre de operación nuevo y estable:

```sh
node --env-file=/RUTA_PRIVADA/admin.env tools/sorteo/admin.mjs rotate /RUTA_PRIVADA/evento ID_PARTICIPANTE reposicion-01
node --env-file=/RUTA_PRIVADA/admin.env tools/sorteo/admin.mjs export /RUTA_PRIVADA/evento
```

El comando persiste el nuevo token antes de contactar con el servidor y compara el hash anterior antes de sustituirlo. Revoca el anterior sin tocar la asignación. Si falla la red, repetir **la misma operación `reposicion-01`**; no inventar otra. Después, entregar solo el enlace nuevo y marcar copias de distribución anteriores como obsoletas. Una segunda sustitución deliberada usa otra operación, p. ej. `reposicion-02`. Si se perdió el journal, restaurar la copia cifrada y comprobar `status`; no iniciar otro sorteo.
